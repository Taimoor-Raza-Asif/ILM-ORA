Findings & Recommendations

High p95 latency at 30–50 VUs Critical
Root Cause MongoDB query queuing and bcrypt CPU saturation under concurrent load. Node.js event loop is blocked during password hashing.
Observed Avg Load p95 = 8,380 ms (SLO: 2,500 ms). Endurance p95 = 4,360 ms.
Recommendation Add MongoDB compound indexes on hot query fields. Reduce bcrypt work factor to 10 or offload hashing to a worker thread pool. Consider adding connection pooling limits.
Register success drops to 23% at 200 VUs (Spike) Critical
Root Cause bcrypt.hash() is synchronous and blocks the Node.js event loop. At 200 VUs the auth service request queue grows faster than it drains, causing timeouts.
Observed 430/559 register checks failed. p95 latency = 30,560 ms during peak VU period.
Recommendation Use Node.js worker_threads for bcrypt operations, or replace with Argon2 (async, lower CPU cost at safe settings). Add a request queue with back-pressure and a 429 rate-limit response.
6.7% error rate at 30–50 VUs Warning
Root Cause Concurrent VUs registering unique emails within short iteration windows occasionally collide on MongoDB unique index, returning 400 "User already exists".
Observed ~1,785 failed requests over 20-min avg-load run. All failures were 400/409, not 5xx.
Recommendation This is a test-script artifact (fast iteration). In production, add proper 409 Conflict responses and client-side retry logic. Email uniqueness constraint is correct behavior.
No memory leak detected (Endurance — 30 min) Good
Finding p95 latency remained flat throughout the 25-minute steady phase (590 ms p50, 4,360 ms p95). No linear growth in response times over time.
Checked All Node.js microservices (8) and the Python DeBERTa service. No process RSS growth observed. MongoDB connection pool stable.
Recommendation No action required. Run a 4-hour soak test before production deployment to confirm at longer timescales.
